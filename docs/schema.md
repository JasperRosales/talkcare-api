# TalkCare Database Schema Design

> Target schema for the OOP refactor described in [`plan.md`](plan.md).
> Canonical roles: **CLIENT**, **ATTORNEY**, **PSYCHIATRIST**, **ADMIN**.
> Legacy role codes are mapped during migration: `USER`/`PEER` → `CLIENT`, `CASE_HANDLER`/`PROFESSIONAL` → `ATTORNEY`, `THERAPIST` → `PSYCHIATRIST`.

---

## 1. Design principles

1. **Class-table inheritance in SQL.** Shared account data lives in `users`; shared person data in `user_profiles`; professional data in `professionals`; role-specific data in `attorneys`, `psychiatrists`, and `admins`. This mirrors the Java hierarchy (`Account` → `Client` / `Professional` → `Attorney` / `Psychiatrist`).
2. **Normalize to 3NF/BCNF.** Role names, service metadata, ID types, concern types, practice areas, specializations, and permissions are lookup tables. Junction tables replace repeated groups. No role-specific nullable columns in `users`.
3. **Single source of truth.** Names/contact data live in `user_profiles`; credentials in `users`; license data in the professional subtype; report status in one column.
4. **Constraint-backed integrity.** FKs, unique indexes, CHECK constraints, and triggers prevent cross-table inconsistencies (e.g. an attorney cannot be assigned to a ThoMatt conversation).
5. **Immutable audit where needed.** `activity_log` records actions; optional `report_snapshots` preserves the reporter details exactly as submitted without polluting normalized tables.

## 2. Entity relationships

```text
roles 1──* users 1──1 user_profiles
              │
              ├──1 clients ────────────────┐
              ├──1 admins                  │
              └──1 professionals 1──1 attorneys ──* attorney_practice_areas *── practice_areas
                              │        └──1 psychiatrists ──* psychiatrist_specializations *── specializations
                              │
service_types 1──* reports ──*─────── assigned_professional_id
      │ 1──* conversations ──1──* messages ──1──* message_attachments
      │ 1──* appointments
      │
      └──* identity_verifications

users 1──* notifications
users 1──* password_reset_tokens
users 1──* activity_log (actor)
roles *──* permissions (role_permissions)
```

## 4. Integrity triggers

### 4.1 Role / subtype consistency

```sql
CREATE OR REPLACE FUNCTION assert_user_role(p_user_id INTEGER, p_role_code VARCHAR)
RETURNS VOID
LANGUAGE plpgsql
AS $$
DECLARE
    actual_code VARCHAR(20);
BEGIN
    SELECT r.code INTO actual_code
    FROM users u
    JOIN roles r ON r.role_id = u.role_id
    WHERE u.id = p_user_id;

    IF actual_code IS NULL THEN
        RAISE EXCEPTION 'User % does not exist', p_user_id USING ERRCODE = '23503';
    END IF;

    IF actual_code <> p_role_code THEN
        RAISE EXCEPTION 'User % must have role %, but has %',
            p_user_id, p_role_code, actual_code
            USING ERRCODE = '23514';
    END IF;
END;
$$;

CREATE OR REPLACE FUNCTION check_client_role() RETURNS TRIGGER
LANGUAGE plpgsql AS $$
BEGIN
    PERFORM assert_user_role(NEW.user_id, 'CLIENT');
    RETURN NEW;
END;
$$;

CREATE TRIGGER clients_role_check
    BEFORE INSERT OR UPDATE OF user_id ON clients
    FOR EACH ROW EXECUTE FUNCTION check_client_role();

CREATE OR REPLACE FUNCTION check_admin_role() RETURNS TRIGGER
LANGUAGE plpgsql AS $$
BEGIN
    PERFORM assert_user_role(NEW.user_id, 'ADMIN');
    RETURN NEW;
END;
$$;

CREATE TRIGGER admins_role_check
    BEFORE INSERT OR UPDATE OF user_id ON admins
    FOR EACH ROW EXECUTE FUNCTION check_admin_role();

CREATE OR REPLACE FUNCTION check_professional_role() RETURNS TRIGGER
LANGUAGE plpgsql AS $$
BEGIN
    PERFORM assert_user_role(NEW.user_id, NEW.professional_type);
    RETURN NEW;
END;
$$;

CREATE TRIGGER professionals_role_check
    BEFORE INSERT OR UPDATE OF user_id, professional_type ON professionals
    FOR EACH ROW EXECUTE FUNCTION check_professional_role();

CREATE OR REPLACE FUNCTION check_attorney_type() RETURNS TRIGGER
LANGUAGE plpgsql AS $$
BEGIN
    PERFORM assert_user_role(NEW.user_id, 'ATTORNEY');
    IF NOT EXISTS (
        SELECT 1 FROM professionals
        WHERE user_id = NEW.user_id AND professional_type = 'ATTORNEY'
    ) THEN
        RAISE EXCEPTION 'User % is not registered as an ATTORNEY professional', NEW.user_id
            USING ERRCODE = '23514';
    END IF;
    RETURN NEW;
END;
$$;

CREATE TRIGGER attorneys_type_check
    BEFORE INSERT OR UPDATE ON attorneys
    FOR EACH ROW EXECUTE FUNCTION check_attorney_type();

CREATE OR REPLACE FUNCTION check_psychiatrist_type() RETURNS TRIGGER
LANGUAGE plpgsql AS $$
BEGIN
    PERFORM assert_user_role(NEW.user_id, 'PSYCHIATRIST');
    IF NOT EXISTS (
        SELECT 1 FROM professionals
        WHERE user_id = NEW.user_id AND professional_type = 'PSYCHIATRIST'
    ) THEN
        RAISE EXCEPTION 'User % is not registered as a PSYCHIATRIST professional', NEW.user_id
            USING ERRCODE = '23514';
    END IF;
    RETURN NEW;
END;
$$;

CREATE TRIGGER psychiatrists_type_check
    BEFORE INSERT OR UPDATE ON psychiatrists
    FOR EACH ROW EXECUTE FUNCTION check_psychiatrist_type();
```

### 4.2 Service / professional specialization consistency

```sql
CREATE OR REPLACE FUNCTION validate_service_assignment(
    p_client_id INTEGER,
    p_professional_id INTEGER,
    p_service_type_id SMALLINT
) RETURNS VOID
LANGUAGE plpgsql AS $$
DECLARE
    required_type VARCHAR(20);
    actual_type   VARCHAR(20);
BEGIN
    PERFORM assert_user_role(p_client_id, 'CLIENT');

    SELECT required_professional_type INTO required_type
    FROM service_types WHERE service_type_id = p_service_type_id;

    SELECT professional_type INTO actual_type
    FROM professionals WHERE user_id = p_professional_id;

    IF actual_type IS NULL THEN
        RAISE EXCEPTION 'Professional % does not exist', p_professional_id
            USING ERRCODE = '23503';
    END IF;

    IF actual_type <> required_type THEN
        RAISE EXCEPTION 'Service % requires a %, but user % is a %',
            p_service_type_id, required_type, p_professional_id, actual_type
            USING ERRCODE = '23514';
    END IF;
END;
$$;

CREATE OR REPLACE FUNCTION validate_conversation() RETURNS TRIGGER
LANGUAGE plpgsql AS $$
BEGIN
    PERFORM validate_service_assignment(NEW.client_id, NEW.professional_id, NEW.service_type_id);
    RETURN NEW;
END;
$$;

CREATE TRIGGER conversations_service_check
    BEFORE INSERT OR UPDATE OF client_id, professional_id, service_type_id ON conversations
    FOR EACH ROW EXECUTE FUNCTION validate_conversation();

CREATE OR REPLACE FUNCTION validate_appointment() RETURNS TRIGGER
LANGUAGE plpgsql AS $$
BEGIN
    PERFORM validate_service_assignment(NEW.client_id, NEW.professional_id, NEW.service_type_id);
    RETURN NEW;
END;
$$;

CREATE TRIGGER appointments_service_check
    BEFORE INSERT OR UPDATE OF client_id, professional_id, service_type_id ON appointments
    FOR EACH ROW EXECUTE FUNCTION validate_appointment();

CREATE OR REPLACE FUNCTION validate_report() RETURNS TRIGGER
LANGUAGE plpgsql AS $$
BEGIN
    PERFORM assert_user_role(NEW.client_id, 'CLIENT');
    IF NEW.assigned_professional_id IS NOT NULL THEN
        PERFORM validate_service_assignment(
            NEW.client_id, NEW.assigned_professional_id, NEW.service_type_id);
    END IF;
    RETURN NEW;
END;
$$;

CREATE TRIGGER reports_assignment_check
    BEFORE INSERT OR UPDATE OF client_id, assigned_professional_id, service_type_id ON reports
    FOR EACH ROW EXECUTE FUNCTION validate_report();
```

### 4.3 `updated_at` maintenance

```sql
CREATE OR REPLACE FUNCTION touch_updated_at() RETURNS TRIGGER
LANGUAGE plpgsql AS $$
BEGIN
    NEW.updated_at := now();
    RETURN NEW;
END;
$$;

CREATE TRIGGER users_touch_updated_at
    BEFORE UPDATE ON users FOR EACH ROW EXECUTE FUNCTION touch_updated_at();
CREATE TRIGGER user_profiles_touch_updated_at
    BEFORE UPDATE ON user_profiles FOR EACH ROW EXECUTE FUNCTION touch_updated_at();
CREATE TRIGGER professionals_touch_updated_at
    BEFORE UPDATE ON professionals FOR EACH ROW EXECUTE FUNCTION touch_updated_at();
CREATE TRIGGER reports_touch_updated_at
    BEFORE UPDATE ON reports FOR EACH ROW EXECUTE FUNCTION touch_updated_at();
CREATE TRIGGER conversations_touch_updated_at
    BEFORE UPDATE ON conversations FOR EACH ROW EXECUTE FUNCTION touch_updated_at();
```

## 10. Normalization notes

### Satisfied forms

- **1NF:** all columns are atomic; multi-valued facts (practice areas, specializations, permissions) use junction tables instead of comma-separated strings or arrays.
- **2NF:** every non-key column depends on the whole primary key; junction tables have no non-key attributes.
- **3NF:** role names, service metadata, ID types, concern types, and permission descriptions are stored once in lookup tables. `users` does not store role names or professional license data. `user_profiles` does not store credentials. Reports reference `client_id` rather than repeating contact data. Messages reference `sender_id` rather than repeating sender name/role.
- **BCNF:** determinants (`roles.code`, `users.username`, `users.email`, `report_code`, `bar_roll_no`, `prc_license_no`) are candidate keys with unique indexes.

### Deliberate exceptions (documented)

| Exception | Why | Control |
|---|---|---|
| `report_snapshots` duplicates reporter contact | Legal/audit history must not change when the client edits their profile | 1:1 with `reports`; written once; never updated |
| File contents on disk (`uploads/`) | Large binaries do not belong in normalized tables | Only URLs/paths are stored; ownership enforced by FK |
| `activity_log.details` free text | Audit events have heterogeneous payloads | Treated as append-only, not queried for business logic |
| `messages.is_auto_reply` boolean | A message is either system-generated or user-authored | CHECK/application enforcement |
| Denormalized aggregate metrics | Admin dashboard counts are computed with `COUNT`/`GROUP BY`, not stored | No materialized counters in the schema |

### Why not single-table inheritance?

A single `users` table with nullable `bar_roll_no`, `prc_license_no`, `law_firm`, `clinic_name`, and `department` would:
- allow an attorney to have a PRC license and a psychiatrist to have a bar number,
- require nullable columns that are meaningless for most rows,
- make unique constraints role-dependent and awkward,
- fail to mirror the Java subtype classes.

Class-table inheritance keeps each subtype's constraints local and matches the OOP hierarchy one-to-one.
